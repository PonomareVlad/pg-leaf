# PostgreSQL → Git: детерминированное файловое представление базы данных

**Статус:** исходная спецификация проекта (v0.1)  
**Язык реализации:** JavaScript  
**Runtime:** Bun  
**Лицензия:** предполагается Open Source, конкретную лицензию выбрать позднее.

---

## 1. Концепция проекта

Необходимо разработать CLI-утилиту, преобразующую обычный SQL-дамп PostgreSQL в иерархическую структуру текстовых SQL-файлов, оптимизированную для хранения и версионирования в Git.

Основная идея:

**Одна запись таблицы PostgreSQL = один стабильный SQL-файл.**

Для записи, имеющей гарантированно уникальный идентификатор, путь к файлу должен определяться этим идентификатором, а не порядком, в котором запись встретилась в дампе.

Это позволит использовать стандартный Git для хранения истории состояний PostgreSQL, не реализуя собственную систему версионирования, diff или дедупликации.

Система должна обеспечивать обратное преобразование файловой структуры в единый SQL-поток, пригодный для восстановления PostgreSQL.

### 1.1. Мотивация

Исходная задача: организовать автоматическое резервное копирование PostgreSQL в Git-репозиторий с последующей публикацией, например, на GitHub.

Традиционные подходы имеют недостатки.

**Бинарные резервные копии**

Архивы, сжатые дампы и другие бинарные представления неудобны для Git. Даже относительно небольшое изменение данных может привести к значительным изменениям бинарного представления.

Кроме того, GitHub ограничивает размер отдельных файлов.

**Единый текстовый SQL-дамп**

Текстовый формат позволяет Git искать и сжимать различия, но монолитный файл также может превысить лимиты GitHub.

**Разделение дампа на фиксированные блоки**

При вставке или удалении записей границы блоков могут смещаться. Это вызывает массовые изменения файлов, даже если сами записи не менялись.

**Отдельные файлы для каждой записи**

Позволяют закрепить стабильный путь за логической записью и сохранить обычный человекочитаемый Git diff.

Именно последний подход необходимо реализовать.

### 1.2. Цель

Получить файловое представление базы PostgreSQL, в котором:

- каждый Git-коммит может соответствовать полному логическому снимку базы;
- изменение одной записи обычно приводит к изменению одного файла;
- добавление записи создаёт файл;
- удаление записи удаляет файл;
- неизменившиеся записи сохраняют идентичное содержимое и путь;
- Git самостоятельно хранит историю изменений;
- можно сравнивать любые коммиты средствами Git;
- можно переключиться на исторический коммит и восстановить соответствующее состояние базы;
- для обычного использования не требуются собственный формат архивов, бинарные контейнеры или внешнее хранилище метаданных.

Целью является не побайтовое сохранение первоначального файла `pg_dump`, а **сохранение его восстановительной семантики**, включая структуру, данные и поддерживаемые служебные объекты.

## 2. Основные принципы

### 2.1. PostgreSQL остаётся источником истины

Не реализовывать собственный механизм дампинга таблиц.

Использовать официальный `pg_dump`.

Утилита работает с результатом его выполнения и не должна подменять штатную функциональность PostgreSQL собственным SQL-экспортёром.

### 2.2. Plain SQL

Основной формат данных: текстовый PostgreSQL SQL.

Не использовать в качестве постоянного представления:

- ZIP;
- GZIP;
- бинарный custom dump;
- Git LFS;
- собственный бинарный формат;
- сериализацию строк в JSON/YAML вместо SQL.

Конечные файлы должны оставаться исполняемым SQL либо частью стандартного SQL-потока PostgreSQL.

### 2.3. Git-нативность

Утилита не должна реализовывать:

- собственный diff;
- собственную историю версий;
- отдельный журнал изменения записей;
- систему дедупликации;
- собственную систему коммитов.

За это отвечает Git.

### 2.4. Отсутствие постоянных манифестов

Дерево файлов должно быть самодостаточным.

Обратная сборка определяется:

1. Иерархией директорий.
2. Соглашением об именовании.
3. Детерминированным порядком обхода.
4. Содержимым SQL-файлов.

Не создавать обязательные `manifest.json`, `index.json` или другие файлы, которые нужно синхронизировать с состоянием базы.

Допускаются временные индексы и служебные структуры во время обработки дампа.

### 2.5. Детерминированность

Одинаковые логические данные при одинаковой схеме, версии инструментов и настройках сериализации должны приводить к одинаковому файловому представлению.

Порядок строк, полученных от `pg_dump`, не должен влиять на имена файлов записей с уникальными ключами.

### 2.6. Безопасность данных

Утилита не должна молча терять, пропускать, объединять или перезаписывать записи из-за ошибок идентификации.

При невозможности безопасно оптимизировать представление допускается менее эффективный, но корректный способ хранения.

Главный приоритет: корректность восстановления.

## 4. Входной формат

### 4.1. Основной источник

Обычный plain-text SQL-дамп PostgreSQL.

Базовый вариант вызова:

```bash
pg_dump \
  --format=plain \
  --column-inserts \
  --rows-per-insert=1 \
  --quote-all-identifiers \
  --encoding=UTF8 \
  --dbname="$DATABASE_URL" \
  > dump.sql
```

Это ориентировочная команда. Реализация должна учитывать доступность опций в поддерживаемых версиях PostgreSQL.

### 4.2. Почему INSERT вместо COPY

Использовать `--column-inserts`.

Этот режим создаёт SQL-команды `INSERT` с явным перечислением колонок.

Например:

```sql
INSERT INTO "public"."users" (
  "id",
  "name",
  "email"
) VALUES (
  '9a48...',
  'Alice',
  'alice@example.com'
);
```

Такое представление:

- является исполняемым PostgreSQL SQL;
- позволяет выделить отдельную запись;
- позволяет сопоставить имена колонок со значениями;
- удобно для стабильного именования файлов;
- потенциально позволяет Git показывать изменения конкретных значений.

Один INSERT должен содержать одну запись.

Для этого явно использовать `--rows-per-insert=1`.

### 4.3. Компромисс производительности

`INSERT` может восстанавливаться существенно медленнее `COPY`.

Это осознанное архитектурное решение.

Приоритет отдаётся читаемости, простоте файлового представления и качеству Git diff.

На начальном этапе не нужно преобразовывать INSERT обратно в COPY.

### 4.4. Неизменность исходной функциональности

Не исключать по умолчанию:

- ограничения;
- индексы;
- внешние ключи;
- sequences;
- триггеры;
- представления;
- функции;
- владельцев;
- права доступа;
- расширения;
- другие объекты, которые штатный `pg_dump` включает в полный дамп.

Не использовать `--data-only`, `--schema-only`, `--no-owner` или `--no-acl` в качестве обязательных настроек.

Это могут быть отдельные пользовательские параметры в будущем.

## 5. Архитектура файлового дерева

### 5.1. Общая структура

PostgreSQL логически делит дамп на секции:

1. `pre-data`;
2. `data`;
3. `post-data`.

Эти секции определяют основной порядок восстановления.

Пример целевого дерева:

```text
snapshot/
├── 00-pre.sql
├── 10-data/
│   ├── schemas/
│   │   └── public/
│   │       ├── cities/
│   │       │   └── rows/
│   │       │       └── ...
│   │       ├── events/
│   │       │   └── rows/
│   │       │       └── ...
│   │       ├── users/
│   │       │   └── rows/
│   │       │       └── ...
│   │       └── registrations/
│   │           └── rows/
│   │               └── ...
│   └── 90-other.sql
└── 20-post.sql
```

**Это концептуальная структура**, а не окончательный стандарт именования. Необходимо разработать порядок исполнения файлов, при котором служебные SQL-команды будут восстановлены корректно.

При необходимости допускаются дополнительные фазовые файлы, например:

```text
00-header.sql
05-pre.sql
10-data/
20-post.sql
99-footer.sql
```

Но не следует создавать лишние фазы без конкретной необходимости.

### 5.2. Назначение частей

`pre-data` содержит определения объектов, необходимых до загрузки данных.

`data` содержит непосредственно записи таблиц и другие данные, включая состояния последовательностей и некоторые специальные объекты.

`post-data` содержит оставшиеся определения, в частности многие индексы и ограничения.

Необходимо сохранить эти сведения и их правильную последовательность.

### 5.3. Важное ограничение

Нельзя считать, что произвольный SQL можно безопасно переставлять.

В частности:

- данные таблиц могут иметь зависимости;
- служебные команды могут влиять на последующее исполнение;
- последовательности требуют правильного восстановления состояния;
- некоторые конструкции PostgreSQL могут требовать особого порядка.

Алгоритм обязан явно определить допустимые перестановки и подтвердить их интеграционными тестами.

Для неизвестной конструкции, положение которой существенно для корректного восстановления, необходимо сохранить исходный порядок или завершить преобразование без публикации результата.

## 6. Основной алгоритм разделения

### 6.1. Последовательность операций

```text
PostgreSQL
    |
    v
  pg_dump
    |
    v
Plain SQL dump
    |
    v
Анализ структуры SQL
    |
    v
Поиск уникальных ключей
    |
    v
Разделение INSERT по записям
    |
    v
Генерация стабильных имён файлов
    |
    v
Форматирование SQL
    |
    v
Дерево SQL-файлов
```

### 6.2. Два прохода

Допускается двухпроходная обработка.

**Первый проход**

Определить:

- SQL-объекты;
- схемы;
- таблицы;
- колонки;
- первичные ключи;
- подходящие уникальные ограничения;
- подходящие уникальные индексы;
- границы секций и блоков.

**Второй проход**

Считать записи таблиц, определить идентификаторы, создать файлы.

Это важно, поскольку определение PRIMARY KEY может находиться в `post-data`, то есть после самих данных таблицы.

### 6.3. Требования к парсеру

Парсер обязан понимать синтаксис, необходимый для безопасного выделения INSERT и значений колонок.

Нельзя использовать примитивное разделение по:

- переводу строки;
- точке с запятой;
- запятой;
- скобкам.

Эти символы могут присутствовать внутри SQL-значений.

Необходимо учитывать:

- строковые литералы;
- экранирование;
- комментарии;
- quoted identifiers;
- долларовые строки;
- вложенные выражения;
- многострочные команды;
- типизированные значения;
- PostgreSQL-специфичный синтаксис.

Предпочтительна потоковая реализация с лексическим анализатором и отдельной логикой для поддерживаемых конструкций `pg_dump`.

Не требуется полноценный SQL-движок.

### 6.4. Неизвестные конструкции

Утилита не должна пытаться интерпретировать весь диалект PostgreSQL.

Неподдерживаемые SQL-объекты можно сохранять как непрозрачные SQL-фрагменты.

Если фрагмент нельзя безопасно разместить в порядке восстановления, необходимо завершить преобразование с ошибкой.

Нельзя пропускать неподдерживаемые объекты молча.

## 7. Идентификация записей

Это центральный механизм проекта.

### 7.1. Основной принцип

Файловый путь записи зависит от гарантированно уникальных значений.

Он не должен зависеть от:

- физического расположения записи;
- PostgreSQL CTID;
- номера строки в дампе;
- времени выполнения экспорта;
- положения записи относительно других записей.

Исключение: таблицы без подходящих уникальных ключей.

### 7.2. Приоритет выбора ключа

Предлагаемый алгоритм:

1. PRIMARY KEY.
2. UNIQUE constraint с гарантированной уникальностью полной комбинации значений.
3. Подходящий UNIQUE INDEX.
4. Порядковый номер записи как резервный механизм.

### 7.3. PRIMARY KEY

Поддерживать:

- числовые ключи;
- UUID;
- текстовые ключи;
- составные ключи;
- другие типы, имеющие стабильное представление в SQL-дампе.

Тип идентификатора не должен требовать специального файлового формата.

### 7.4. UNIQUE

Уникальный ключ можно использовать, только когда PostgreSQL гарантирует отсутствие двух записей с одинаковой выбранной комбинацией значений.

Поддержать:

- UNIQUE по одному столбцу, который не допускает NULL;
- составной UNIQUE по подходящим столбцам;
- UNIQUE NULLS NOT DISTINCT при корректном определении его семантики;
- обычные полные уникальные индексы, если все необходимые условия доказаны.

Не считать автоматически пригодными:

- обычный неуникальный INDEX;
- FOREIGN KEY;
- частичный UNIQUE INDEX;
- уникальный индекс на выражении;
- UNIQUE со значениями NULL, допускающий несколько совпадений.

Последние случаи можно поддержать в следующих версиях, но только при доказуемой корректности.

### 7.5. Выбор между несколькими ключами

Если существует несколько пригодных уникальных ключей:

- PRIMARY KEY имеет безусловный приоритет;
- остальные кандидаты выбираются по фиксированному детерминированному правилу;
- порядок их появления в дампе не должен случайным образом менять выбор.

При изменении схемы допускается изменение ключа и последующее массовое переименование файлов.

Не требуется сохранять историю идентификаторов между миграциями.

## 8. Хеширование ключей

### 8.1. Алгоритм

Использовать SHA-256.

Хешировать не содержимое всей записи, а представление значений выбранного уникального ключа.

Это гарантирует стабильность пути при изменении обычных неключевых полей.

### 8.2. Составные ключи

Не выполнять простую конкатенацию значений через произвольный разделитель.

Например, комбинации:

```text
["ab", "c"]
["a", "bc"]
```

не должны допускать одинакового кодирования.

Использовать однозначную сериализацию с явными границами значений, порядком компонентов и обработкой NULL.

Возможный принцип:

```text
Количество компонентов
Длина компонента 1
Байты компонента 1
Длина компонента 2
Байты компонента 2
...
```

В том числе необходимо различать SQL NULL и текстовое значение `"NULL"`.

Хешировать полученную байтовую последовательность.

### 8.3. Стабильность

Функция получения хеша должна быть:

- чистой;
- детерминированной;
- независимой от локали ОС;
- независимой от порядка обхода строк;
- одинаковой для всех поддерживаемых ключей.

Идентификатор таблицы можно учитывать в области хеширования, хотя размещение в директории таблицы уже обеспечивает логическую изоляцию.

### 8.4. Пример

```text
users/
  rows/
    a3/
      a3c4...f2.sql
    b7/
      b7e1...91.sql
```

Полный SHA-256 должен использоваться в имени файла.

Подкаталоги из начальных байтов хеша нужны для равномерного распределения файлов.

### 8.5. Коллизии

Нельзя молча перезаписывать файл, если уже встречен тот же путь для другой записи.

При конфликте:

- определить причину;
- отличить дублированный уникальный ключ от хеш-коллизии или ошибки парсера;
- остановить экспорт с диагностикой.

Не допускать потери записей.

## 9. Таблицы без уникального ключа

### 9.1. Принятое решение

**Разделять абсолютно все таблицы на отдельные записи**, даже если уникальный ключ отсутствует.

Не оставлять всю такую таблицу в едином файле.

### 9.2. Резервный алгоритм

Если невозможно доказать уникальность записей, использовать их порядковые номера во входном дампе.

Пример:

```text
participants/
  rows/
    000000000001.sql
    000000000002.sql
    000000000003.sql
```

Нумерация начинается с заранее установленного значения.

Для лексикографической сортировки использовать фиксированную ширину чисел, достаточную для практически применимых объёмов, либо иной детерминированный числовой формат с гарантированно корректной сортировкой.

### 9.3. Допускаемый недостаток

Физический порядок PostgreSQL не гарантирует стабильного порядка строк между дампами.

Возможна ситуация:

```text
До:
1.sql -> Alice
2.sql -> Bob
3.sql -> Charlie

После:
1.sql -> David
2.sql -> Alice
3.sql -> Bob
4.sql -> Charlie
```

Git увидит множество изменений.

**Это осознанно допустимое поведение.**

Не нужно пытаться реализовать дополнительный алгоритм сопоставления таких записей.

### 9.4. Дублированные записи

Если в таблице находятся две полностью идентичные записи, должны появиться два отдельных файла.

Именно поэтому запрещено использовать хеш всего содержимого записи в качестве единственного идентификатора при отсутствии уникального ключа.

## 10. Человекочитаемость SQL

### 10.1. Цель форматирования

Желательно, чтобы Git diff показывал изменения конкретных колонок, а не всю SQL-команду одной строкой.

Пример целевого формата:

```sql
INSERT INTO "public"."users" (
  "id",
  "username",
  "email",
  "balance"
) VALUES (
  '85c1...',
  'alice',
  'alice@example.com',
  120
);
```

При изменении `balance` с `120` на `180` Git должен по возможности отображать изменение соответствующей строки.

### 10.2. Использование существующего форматтера

Не писать полноценный собственный SQL-форматтер.

Рассмотреть готовый JavaScript-пакет `sql-formatter` с диалектом PostgreSQL.

Требования:

- детерминированный вывод;
- стабильные отступы;
- LF;
- отсутствие изменения SQL-литералов;
- сохранение исполняемости SQL;
- корректность для используемого синтаксиса pg_dump.

### 10.3. Ограничения форматирования

Не форматировать произвольные определения функций, триггеров и другие сложные SQL-объекты без необходимости.

Основная цель форматирования: INSERT записей.

Если форматтер не поддерживает конкретный INSERT, допустимо сохранить его исходное представление без потери данных.

Если форматтер изменяет семантику SQL, его результат использовать запрещено.

Нужно обязательно проверить этот аспект интеграционными тестами.

### 10.4. Каноничность

При одинаковом входном INSERT результат форматирования обязан совпадать побайтово.

Не добавлять:

- временные метки;
- идентификаторы текущего запуска;
- случайные пробелы;
- переменные комментарии;
- нестабильные служебные поля.

## 11. Восстановление

### 11.1. Основной принцип

Дерево SQL-файлов должно преобразовываться в единый SQL-поток.

Необязательно создавать промежуточный монолитный файл.

### 11.2. Пример

```text
Дерево файлов
     |
     v
Детерминированный обход
     |
     v
Последовательный SQL-поток
     |
     v
psql
     |
     v
PostgreSQL
```

### 11.3. Исполнение

Для plain SQL использовать `psql`.

Пример внешнего вызова:

```bash
tool join ./snapshot --stdout |
  psql -X -v ON_ERROR_STOP=1 -d target_database
```

Синтаксис CLI утилиты пока условный.

`pg_restore` не является основным инструментом восстановления plain SQL.

### 11.4. Детерминированный порядок

Обход файлов должен явно использовать установленную сортировку.

Не полагаться на порядок выдачи файлов операционной системой.

Не использовать локалезависимое сравнение.

Каждый файл должен попадать в SQL-поток ровно один раз.

Между независимыми SQL-командами должны сохраняться корректные разделители.

### 11.5. Семантическая эквивалентность

Восстановленная база должна быть логически эквивалентна той, из которой был создан исходный дамп.

Не требуется побайтовое совпадение:

```text
original.sql == reconstructed.sql
```

Требуется корректное восстановление:

```text
restore(original.sql)
≈
restore(reconstructed.sql)
```

Здесь эквивалентность означает совпадение поддерживаемой схемы, данных и служебного состояния, а не физического расположения строк.

Это важно: сортировка записей по именам файлов может отличаться от исходного порядка `pg_dump`.

### 11.6. Предположения

Восстановление по умолчанию выполняется в чистую, подходящую базу PostgreSQL.

Автоматическое объединение снимка с уже заполненной базой не входит в первую версию.

---

## 12. Служебные объекты PostgreSQL

Утилита не должна считать, что секция data содержит исключительно INSERT строк обычных таблиц.

Необходимо исследовать и поддержать сохранение:

- значений sequences;
- large objects;
- данных partitioned tables;
- materialized views;
- идентичностей и generated columns;
- служебных операторов PostgreSQL;
- других инструкций стандартного plain dump.

### 12.1. Последовательности

Типовой SQL может содержать:

```sql
SELECT pg_catalog.setval(
  'public.users_id_seq',
  42,
  true
);
```

Такие команды необходимо сохранять.

После восстановления новые INSERT должны продолжать работу с корректным состоянием последовательностей.

### 12.2. Large objects

Large objects PostgreSQL могут храниться вне обычных строк пользовательских таблиц.

Их нельзя считать частью конкретной записи только на основании внешнего ключа или OID.

Необходимо сохранять их штатное представление в дампе.

### 12.3. Extensions и специальные объекты

Не преобразовывать самостоятельно сложные объекты PostgreSQL.

По возможности сохранять SQL, сформированный `pg_dump`, без изменений.

При обнаружении неподдерживаемой конструкции, опасной для восстановления, не создавать заведомо некорректный снимок.

---

## 13. Поведение при изменении схемы

### 13.1. Принятое решение

Схема базы может изменяться произвольным образом.

Например:

- добавлены таблицы;
- удалены таблицы;
- изменены колонки;
- изменён PRIMARY KEY;
- заменён UNIQUE INDEX;
- переименованы объекты.

Специальные миграции файлового представления не требуются.

### 13.2. Полная регенерация

Каждый экспорт формирует новое дерево целиком.

Не пытаться инкрементально редактировать предыдущий снимок на основе предыдущих ключей.

Алгоритм:

1. Получить актуальный дамп.
2. Сгенерировать новое файловое дерево во временной директории.
3. Проверить завершённость генерации.
4. Заменить ранее созданное дерево.
5. Предоставить Git возможность самостоятельно определить изменения.

### 13.3. Breaking changes

При изменении схемы допускаются массовые Git diff.

Например, изменение PRIMARY KEY может переименовать все файлы таблицы.

Это нормальный результат.

Не нужна миграционная карта соответствия старых и новых ключей.

---

## 14. Совместимость PostgreSQL

### 14.1. Принятое решение

Не пытаться обеспечить абсолютно одинаковую текстовую сериализацию между произвольными major-версиями PostgreSQL.

Если изменился вывод `pg_dump`, допускаются изменения представления файлов.

### 14.2. Не требуется

- вести историю версий `pg_dump`;
- сравнивать их между экспортами;
- блокировать обновления PostgreSQL;
- предупреждать о каждом изменении версии;
- нормализовать различия между major-версиями только ради Git diff.

### 14.3. Обязательное условие

Инструмент должен сохранять корректность данных в рамках поддерживаемого входного формата.

Если синтаксис нового `pg_dump` изменился и текущий парсер его не поддерживает, нельзя молча повреждать снимок.

Семантические ошибки и отсутствие поддержки синтаксиса отличаются от обычного изменения текстового представления.

---

## 15. Большие записи и ограничения GitHub

### 15.1. Принятое решение

**Один SQL-файл на одну запись независимо от её размера.**

Не разделять отдельный INSERT на несколько файлов.

### 15.2. Пример

Если отдельная запись содержит бинарные или текстовые данные размером 150 МБ, утилита должна попытаться создать полноценный SQL-файл с этой записью.

Не вводить искусственный лимит 100 МБ внутри утилиты.

### 15.3. Не требуется

- нарезка одной записи по байтам;
- нарезка по столбцам;
- Content-Defined Chunking;
- отдельное бинарное хранение полей;
- проверка лимитов GitHub перед записью;
- автоматический переход на Git LFS.

### 15.4. Взаимодействие с GitHub

Если созданный файл превышает допустимый размер GitHub, соответствующая ошибка должна возникнуть на уровне Git/GitHub во время публикации.

Сам инструмент не должен дублировать эту проверку или вводить специальную обработку.

Это сознательная граница ответственности.

### 15.5. Ограничения масштабирования

Следует документировать, что помимо лимита отдельных файлов GitHub имеет рекомендации и ограничения по:

- размеру репозитория;
- размеру push;
- числу объектов;
- производительности операций Git.

Утилита не обещает бесконечное масштабирование GitHub.

Её задача: генерировать максимально Git-дружественное представление.

---

## 16. Работа с файловой системой

### 16.1. Кодировка

Основная кодировка: UTF-8.

Использовать стандартные механизмы Bun для обработки UTF-8.

При генерации `pg_dump` явно обеспечивать UTF-8, если это требуется для консистентности входного файла.

### 16.2. Переводы строк

Использовать LF.

Пример `.gitattributes`:

```gitattributes
*.sql text eol=lf
```

Внутри утилиты также генерировать единообразные переводы строк.

### 16.3. Именование директорий

Обеспечить совместимость путей с распространёнными файловыми системами Windows, macOS и Linux.

Учесть:

- регистр символов;
- специальные символы;
- Unicode;
- зарезервированные имена файлов;
- максимальную длину имени;
- совпадения имён при регистронезависимом сравнении.

Использовать детерминированное безопасное кодирование имён схем и таблиц.

Желательно сохранять их человекочитаемость.

При необходимости допустимо добавлять короткий стабильный идентификатор для исключения коллизий.

### 16.4. Иерархическое распределение

Не складывать миллионы файлов в одну директорию.

Для SHA-256 использовать директории по префиксам хеша.

Для числовых идентификаторов также предусмотреть детерминированную разбивку директорий при большом числе записей.

Не менять расположение существующей записи из-за роста количества записей.

### 16.5. Атомарность обновления

Не удалять рабочий снимок до успешного завершения нового экспорта.

Предпочтительный механизм:

1. Создать временную рабочую директорию.
2. Выполнить экспорт и преобразование.
3. Проверить завершённость.
4. Заменить предыдущую директорию готовым деревом.
5. Удалить временные данные.

Если экспорт завершился ошибкой, предыдущий снимок должен остаться доступным.

Все удаления ограничивать управляемой директорией снимка.

Нельзя случайно удалить корень Git-репозитория или пользовательские файлы.

## 17. Ограничение потребления ресурсов

### 17.1. Потоковая архитектура

Объём памяти не должен линейно расти вместе с общим размером базы.

Нельзя читать весь SQL-дамп в память.

Обрабатывать поток последовательно, с ограниченным буфером.

### 17.2. Двухпроходный парсинг

Если необходим второй проход, разрешается использовать временный файл исходного дампа.

Это предпочтительнее хранения полного дампа в RAM.

### 17.3. Размер отдельной записи

Размер крупнейшей записи может определять необходимое количество памяти для некоторых операций, включая форматирование.

По возможности обрабатывать большие INSERT без создания множества полноразмерных копий строки.

При невозможности безопасного форматирования очень большой записи допустимо сохранить её исходный SQL без форматирования.

### 17.4. Производительность

Проект не обязан быть быстрее стандартного `pg_dump`.

Главные приоритеты:

1. Корректность.
2. Детерминированность.
3. Читаемость.
4. Масштабируемость.
5. Производительность.

## 18. CLI

### 18.1. Основные команды

Предусмотреть три операции.

**Split**

Преобразование существующего дампа в дерево:

```bash
tool split dump.sql --output ./snapshot
```

**Join**

Восстановление единого SQL:

```bash
tool join ./snapshot --output restored.sql
```

Потоковое восстановление:

```bash
tool join ./snapshot --stdout |
  psql -X -v ON_ERROR_STOP=1 -d target_database
```

**Dump**

Обёртка над `pg_dump`, вызывающая экспорт и последующее разделение:

```bash
tool dump \
  --database "$DATABASE_URL" \
  --output ./snapshot
```

Это проектные имена команд. Окончательный CLI можно уточнить при реализации.

### 18.2. Дополнительные требования

- CLI должен возвращать корректные exit codes.
- Ошибки направлять в stderr.
- При выдаче SQL в stdout не смешивать SQL и служебные сообщения.
- Поддерживать выполнение из CI.
- Не требовать интерактивного ввода.
- Корректно обрабатывать прерывания и ошибки подпроцессов.
- Не выводить в логи пароли и полные строки подключения с секретами.

### 18.3. Работа с Git

Git не должен быть обязательной зависимостью операций `split` и `join`.

Не нужно автоматически делать `git commit`, `git push`, создавать репозитории или настраивать GitHub.

Эти операции выполняются внешней автоматизацией.

Это позволит использовать инструмент независимо от GitHub.

## 19. Пример использования в Git

Типовой внешний процесс:

```text
Запуск по расписанию
        |
        v
pg_dump
        |
        v
Формирование нового дерева
        |
        v
Замена предыдущего снимка
        |
        v
git add -A
        |
        v
git commit
        |
        v
git push
```

В случае отсутствия изменений можно пропустить создание коммита.

Каждый успешно созданный коммит соответствует определённому снимку базы.

При переходе на исторический коммит:

```text
git checkout <commit>
        |
        v
tool join
        |
        v
psql
```

История состояний обеспечивается самим Git.

## 20. Тестирование

Тестирование является обязательной частью проекта.

### 20.1. Среда

Использовать:

- `bun test`;
- временные директории;
- тестовые SQL fixtures;
- PostgreSQL в Docker для интеграционных тестов.

Тесты не должны требовать рабочую пользовательскую базу или GitHub.

### 20.2. Юнит-тесты

Проверить:

- SQL-токенизацию;
- выделение INSERT;
- разбор имён таблиц;
- сопоставление колонок и значений;
- обнаружение PRIMARY KEY;
- обнаружение UNIQUE;
- составные ключи;
- сериализацию ключей;
- SHA-256;
- генерацию путей;
- резервную нумерацию;
- сортировку файлов;
- обработку коллизий.

### 20.3. Тесты детерминированности

Создать два дампа с одинаковыми записями, но разным порядком строк.

Для таблиц с ключами результат должен содержать:

- одинаковые пути;
- одинаковые файлы;
- одинаковый итоговый SQL-поток после сборки.

Проверить ситуацию, когда изменилось только одно неключевое поле.

Ожидаемый результат: изменяется только файл соответствующей записи.

### 20.4. Тесты таблиц без ключей

Проверить:

- одинаковые записи;
- вставку новой записи в начале;
- вставку в середине;
- удаление записи;
- изменение порядка;
- большое число записей.

Все исходные записи должны восстанавливаться с сохранением кратности.

### 20.5. SQL edge cases

Обязательно проверить:

- NULL;
- пустую строку;
- Unicode;
- кириллицу;
- emoji;
- кавычки;
- обратные слеши;
- переносы строк внутри значений;
- SQL-комментарии внутри строк;
- JSON/JSONB;
- массивы;
- UUID;
- BYTEA;
- большие TEXT;
- временные значения;
- numeric;
- составные ключи;
- quoted identifiers;
- специальные имена таблиц;
- несколько схем с одинаковыми названиями таблиц.

### 20.6. Интеграционный Round Trip

Главный сценарий:

```text
Исходная PostgreSQL
        |
        v
      pg_dump
        |
        v
       split
        |
        v
       join
        |
        v
       psql
        |
        v
Восстановленная PostgreSQL
```

После восстановления сравнить:

- набор таблиц;
- определения схем;
- ограничения;
- индексы;
- количество записей;
- значения записей;
- кратность одинаковых записей;
- состояния sequences;
- специальные поддерживаемые объекты.

Для сравнения использовать логическое содержимое, а не физический порядок строк.

### 20.7. Git-тесты

Создать временный Git-репозиторий.

Последовательность:

1. Первый экспорт.
2. Commit.
3. Повторный экспорт без изменений.
4. Проверка отсутствия изменений.
5. Изменение одной записи.
6. Повторный экспорт.
7. Проверка, что изменён ожидаемый файл.
8. Добавление записи.
9. Удаление записи.
10. Проверка Git diff.

Дополнительно проверить смену схемы и массовую перегенерацию.

### 20.8. Тестирование ошибок

Проверить:

- невалидный SQL;
- повреждённый дамп;
- обрыв потока;
- ошибку `pg_dump`;
- ошибку записи файлов;
- отсутствие прав;
- недостаток свободного места;
- столкновение имён;
- неподдерживаемую структуру;
- ошибку восстановления через `psql`;
- завершение процесса во время генерации.

Ни один из этих сценариев не должен оставлять ошибочно опубликованный завершённый снимок.

### 20.9. Тесты крупных записей

Проверить создание SQL-файла размером более 100 МБ.

Не вводить специального ограничения размера.

GitHub в этом тесте не требуется.

Проверяется поведение самой утилиты и отсутствие неявного разделения строки.

## 21. Безопасность

### 21.1. Содержимое дампов

Дамп PostgreSQL может содержать персональные данные, токены, пароли и другие секреты.

Сам исходный код утилиты может быть открытым.

Это не означает, что репозитории с резервными копиями должны быть публичными.

Утилита не должна автоматически публиковать данные.

### 21.2. SQL при восстановлении

SQL-дампы являются исполняемыми сценариями.

Не выполнять неизвестные или недоверенные дампы автоматически.

Учитывать специальные команды `psql`, включая появившиеся в новых версиях механизмы ограниченного режима.

### 21.3. Временные файлы

Не оставлять временные копии чувствительных данных после успешного выполнения.

Учитывать права доступа к временным директориям.

### 21.4. Команды ОС

Не собирать shell-команды через небезопасную конкатенацию пользовательских аргументов.

Использовать безопасный запуск подпроцессов Bun.

## 22. Особые технические вопросы

Эти пункты необходимо исследовать непосредственно во время разработки.

### 22.1. Структура plain dump

Проверить надёжный способ выделения секций pre-data, data и post-data из единого дампа.

Не завязываться исключительно на комментарии, если они не дают достаточной гарантии.

Разделение на секции должно быть обосновано фактическим форматом вывода `pg_dump`.

### 22.2. Метаданные ключей

Реализовать определение пригодных ключей из SQL-определений, содержащихся в исходном дампе.

Не требовать отдельного подключения к живой базе только для определения PRIMARY KEY, если эту информацию можно безопасно извлечь из дампа.

Если конкретная конструкция не поддерживается, использовать резервную нумерацию вместо предположения об уникальности.

### 22.3. Нестабильные служебные данные

Исследовать динамические поля в SQL-выводе `pg_dump`, которые могут изменяться при каждом запуске без изменения базы.

В частности, некоторые версии PostgreSQL добавляют случайный ключ для команд ограниченного режима `psql`.

Нельзя заменять такой ключ заранее известным постоянным значением только ради одинаковых дампов, если это ухудшает безопасность.

При необходимости реализовать безопасную обработку с генерацией нового случайного значения во время сборки SQL.

### 22.4. Форматирование

Проверить, что выбранный форматтер действительно корректно обрабатывает PostgreSQL INSERT с различными типами данных.

Не полагаться только на визуальную корректность полученного SQL.

### 22.5. Сложные схемы

Проверить:

- partitioned tables;
- наследование;
- составные PK;
- NULLS NOT DISTINCT;
- GENERATED ALWAYS AS IDENTITY;
- generated columns;
- таблицы без пользовательских колонок;
- большие объекты.

Поддержку допустимо расширять поэтапно, но без молчаливой потери данных.

## 24. Критерии готовности

Первую рабочую версию можно считать готовой, если выполняются следующие условия.

1. Инструмент принимает SQL-дамп, созданный поддерживаемой версией `pg_dump`.
2. Формирует самодостаточное дерево SQL-файлов.
3. Для таблиц с поддерживаемым уникальным ключом генерирует стабильные пути по SHA-256.
4. Для таблиц без ключей использует порядковую нумерацию.
5. Не теряет полностью идентичные записи.
6. Не разрезает отдельные INSERT на несколько файлов.
7. Создаёт файлы независимо от их размера, в пределах возможностей ОС и runtime.
8. Позволяет потоково восстановить единый SQL.
9. Восстанавливает тестовую PostgreSQL без потери данных.
10. Не генерирует изменений файлов при повторном экспорте неизменившейся базы в одинаковых условиях.
11. Обновляет только ожидаемые файлы при изменении отдельных записей с неизменными уникальными ключами.
12. Корректно переживает изменение схемы за счёт полной регенерации дерева.
13. Не требует GitHub для локального тестирования.
14. Не требует манифеста для восстановления.
15. Не повреждает предыдущий снимок при неудачном новом экспорте.
16. Не содержит собственной системы истории или diff.
17. Работает на JavaScript/Bun.

## 27. Главный принцип для разработчика

**Не пытаться построить новую систему резервного копирования PostgreSQL вместо существующих инструментов.**

Нужно создать детерминированный промежуточный формат, который связывает стандартный PostgreSQL SQL-дамп со стандартной файловой моделью Git.

`pg_dump` отвечает за извлечение данных.

Наша утилита отвечает за их безопасное и стабильное файловое представление.

`psql` отвечает за восстановление.

Git отвечает за историю, сравнение и хранение изменений.

GitHub либо другой Git remote отвечает за удалённое хранение.

Каждый компонент должен выполнять свою задачу, без дублирования функциональности остальных.
