# pg-leaf: MVP Specification

## Концепция

**pg-leaf** — локальный CLI-инструмент на **Bun / JavaScript** для обратимого разделения PostgreSQL SQL-дампов на независимые файлы, удобные для хранения в Git.

**Цель MVP:** реализовать минимальный рабочий прототип `split → join`, сохраняющий исходный SQL без потерь.

## Использование

```sh
pg-leaf split dump.sql output   # разделить дамп на чанки (директория очищается)
pg-leaf join output dump.sql    # собрать дамп обратно
bun test                        # запустить тесты
```

`join` рекурсивно обходит директорию и конкатенирует чанки в алфавитном порядке.

## Алгоритм

Однопроходный потоковый разбор SQL построчно.

Парсер представляет собой простой **конечный автомат (state machine)**, переключающий состояния по служебным комментариям `pg_dump`.

Пример сигнатуры:

```sql
-- Data for Name: users; Type: TABLE DATA; Schema: public; Owner: postgres
```

При обнаружении соответствующего заголовка автомат завершает текущий чанк и открывает следующий.

### Состояния

| State | Поведение |
|---|---|
| `HEADER` | Накапливает содержимое до первого `TABLE DATA` |
| `TABLE_DATA` | Создаёт отдельный SQL-файл для каждой таблицы |
| `FOOTER` | Накапливает содержимое после последнего `TABLE DATA` |

Переход `TABLE_DATA → FOOTER` определяется по первому заголовку объекта, не относящемуся к `TABLE DATA`.

Все строки, включая комментарии и форматирование, сохраняются без изменений.

## Структура результата

```text
output/
├── 1.sql            # header
├── 2/               # table data: схема → таблица → чанки
│   └── public/
│       └── users/
│           ├── _.sql        # всё, кроме INSERT (комментарии секции и т.п.)
│           ├── <hash>.sql   # один INSERT = один файл, имя — sha256 значений уникального ключа (PK > UNIQUE) или всего содержимого
│           └── <hash>.2.sql # дубликаты получают суффикс .2, .3…
└── 3.sql            # footer
```

`join` восстанавливает SQL рекурсивной конкатенацией чанков в алфавитном порядке: нумерация `1 / 2 / 3` держит header, data и footer на своих местах, а `_.sql` внутри таблицы сортируется перед hash-чанками.

Для таблиц с уникальным ключом (ключ берётся из `PRIMARY KEY`, иначе — первого `UNIQUE` в constraints дампа) хэш считается по значениям ключевых колонок: изменение остальных колонок меняет содержимое чанка, но не его имя — diff остаётся точечным. Таблицы без ключа используют хэш полного содержимого INSERT.

Для MVP предполагается, что сегменты `TABLE DATA` идут подряд.

## Принципы реализации

- **Stack:** Bun, JavaScript, нативные API, минимум зависимостей.
- **Архитектура:** streaming + state machine + `switch` по сигнатурам комментариев.
- **Стиль:** компактный, функциональный, современный, самодокументируемый код.
- **KISS:** без полноценного SQL-парсера, AST и избыточных абстракций.
- **Расширяемость:** возможность добавлять обработчики новых типов сегментов.
- **Ограничения:** неподдерживаемые сценарии документируются как `limitations`, не усложняя MVP.

## Проверка работоспособности

Минимальный набор реальных SQL-фикстур и автоматических тестов:

1. `split` создаёт ожидаемые чанки.
2. `join` собирает валидный дамп, `join(split(x))` сходится к неподвижной точке: `join(split(join(split(x)))) === join(split(x))`.
3. Каждая строка исходного дампа сохраняется без потерь (включая дубликаты).

## Limitations

- Поддерживается только стандартный plain-text вывод `pg_dump` с его служебными комментариями; для разделения данных на записи дамп должен быть снят с `--inserts`.
- Сегменты `TABLE DATA` должны идти подряд: первый не-`TABLE DATA` заголовок после них начинает `footer`.
- `join` собирает INSERT-чанки в порядке hash-имён, поэтому порядок записей внутри таблицы не сохраняется (результат эквивалентен, но не побайтово идентичен исходнику).
- Конец INSERT определяется по строке, оканчивающейся на `;` — значения с переводом строки и `;` в конце строки внутри литерала не поддерживаются.
- `COPY`-данные (дамп без `--inserts`) не разделяются на записи и целиком попадают в `_.sql` таблицы.
- Стабильные хэши работают для позиционных INSERT (`--inserts` без `--column-inserts`): порядок значений сопоставляется с порядком колонок из `CREATE TABLE`; при несовпадении числа значений выполняется fallback на хэш содержимого.

## За пределами MVP

- Оптимизация Git-diff.
- Поддержка нестандартных SQL-дампов.

## Критерий готовности

Минимальная читаемая реализация, которая разбирает реальный SQL-дамп на `header / table data / footer` и собирает его обратно без потерь.

**Приоритет:** простота реализации и ревью, а не универсальность или производительность.
